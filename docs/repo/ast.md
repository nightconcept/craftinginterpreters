# The AST and Part II

This spoke is the output of Phase 2.5. It decides the shape of the syntax
tree, how passes dispatch over it, how control flow leaves a function, and
who owns an `Environment`. Chapters 5 to 13 and Appendix II follow it.

Every claim here was compiled and run against the pinned V 0.5.2. Where a
decision rests on a language limit, the exact compiler message is quoted.

## The problem

Nystrom's `Expr` is an abstract Java class with a nested static subclass per
node type, generated by a tool, and every pass over the tree is a
`Visitor<R>` implementation reached by double dispatch through `accept()`.
Three Java features carry that design: subclass polymorphism, generic
interfaces, and method overloading. V has one of the three.

## Survey: what other translations did

No V implementation of Lox exists. The book's wiki lists none, and a GitHub
repository search for `lox language:V` returns zero. There was no precedent
to copy, so the survey looked at the nearest languages instead.

| Implementation | Language | Approach |
| --- | --- | --- |
| [Shri333/golox](https://github.com/Shri333/golox) | Go | Faithful visitor: `ExprVisitor` interface, `Accept` per node, `interface{}` return |
| [chidiwilliams/glox](https://github.com/chidiwilliams/glox) | Go | Faithful visitor, same shape |
| [rockcavera/nim-nlox](https://github.com/rockcavera/nim-nlox) | Nim | Dropped the visitor. Kept the class hierarchy, dispatched with open multi-methods: `method evaluate(expr: Binary, ...)` |
| [abesto/jlox-rs](https://github.com/abesto/jlox-rs) | Rust | Hybrid: `enum Expr`, plus a macro generating both an `ExprVisitor` trait and a `walk()` that is one `match` |
| Rust, ~50 further ports | Rust | Overwhelmingly `enum` + `match`, visitor discarded |

The pattern is consistent. Languages with interfaces and dynamic dispatch
kept the visitor because it cost nothing. Languages with sum types went
against the book and used their native dispatch. Nobody reproduced Java's
generic `Visitor<R>` verbatim, because most of them could not.

V is the unusual case: it has *both* sum types and generic interfaces.

## Decision 1: a sum type for storage, a visitor for dispatch

`Expr` is a V sum type. Dispatch goes through a generic visitor interface
and a single `walk_expr` function that performs the `match` once.

```v
type Expr = BinaryExpr | GroupingExpr | LiteralExpr | UnaryExpr

interface ExprVisitor[R] {
mut:
	visit_binary_expr(e BinaryExpr) !R
	visit_grouping_expr(e GroupingExpr) !R
	visit_literal_expr(e LiteralExpr) !R
	visit_unary_expr(e UnaryExpr) !R
}

fn walk_expr[R](e Expr, mut visitor ExprVisitor[R]) !R {
	return match e {
		BinaryExpr { visitor.visit_binary_expr(e)! }
		GroupingExpr { visitor.visit_grouping_expr(e)! }
		LiteralExpr { visitor.visit_literal_expr(e)! }
		UnaryExpr { visitor.visit_unary_expr(e)! }
	}
}
```

This is verified working, generic parameter and all. It keeps the book's
vocabulary — a visitor interface, one `visit_*` method per node type, a pass
that implements the interface — while writing `match` exactly once instead
of writing `accept()` twelve times.

### Why not a bare `match`

Section 5.3 of Representing Code spends roughly two thousand words teaching
the Visitor pattern and the Expression Problem, and that prose cannot
change. Under a bare `match` the chapter would teach a pattern the code
never contains, and eight of the chapter's eighteen `^code` tags would have
no counterpart. The hybrid keeps them.

### Why not the faithful visitor

Because V cannot express it. A per-node `accept` needs a generic method on
the `Expr` interface, and the compiler rejects that:

```
error: non-generic interface `Expr` cannot define a generic method
```

The workaround is one visitor interface and one differently-named accept per
return type — `accept_value`, `accept_string`, `accept_void` — because V has
no method overloading either. That is a larger divergence from the book than
the hybrid, paid for in every chapter from 5 to 13, in exchange for nothing.
The Go ports avoided this only because Go's `interface{}` let them collapse
every return type into one.

### Names: every variant carries its base name

`Expr.Binary` becomes `BinaryExpr`; `Stmt.If` becomes `IfStmt`. V has one
flat namespace, so Java's nesting has to go somewhere, and the suffix is
where the Go ports put it.

It is not only cosmetic. `Literal` is already taken by chapter 4's token
literal type in `token.v`, `Expr.Expression` and `Stmt.Expression` would
collide, and `If`, `While`, and `Return` are poor bare type names in V. The
suffix removes all of it at once, and it makes the visitor method names read
exactly like Nystrom's: `visitBinaryExpr` is `visit_binary_expr`.

### Every visit method returns `!R`

Java's visit methods can throw — `RuntimeError` in chapter 7, `Return` in
chapter 10 — because those are unchecked exceptions. `!R` says the same
thing in V's vocabulary, and it means one `walk_expr` serves the printer,
the interpreter, and the resolver alike. A pass that cannot fail simply
never returns an error; its callers still write `!` or `or {}`.

## Decision 2: recursion needs no pointers

Plan question 2 asked whether `Expr` containing `Expr` needs a reference or
a heap allocation. It needs neither. This compiles and runs:

```v
struct BinaryExpr {
	left     Expr
	operator Token
	right    Expr
}
```

V boxes struct variants of a sum type, so the recursion terminates without
`&Expr`, without `[heap]`, and without any explicit allocation. The
snippets therefore render as plain field declarations with no pointer
syntax for a reader to trip over, and `match` smart-casts `e` to the variant
type inside each arm with no cast.

## Decision 3: no `GenerateAst`

Nystrom writes a Java program that prints Java source. V needs no generator:
a sum type plus four structs *is* the type description that his
`Arrays.asList("Binary : Expr left, ...")` encodes. `vlox/` gains no tool
directory, and there is nothing in `vlox/src` corresponding to the writer
boilerplate.

Four of chapter 5's eighteen tags describe that boilerplate and have no V
counterpart at all. They keep rendering the placeholder, and a translator's
note next to each explains why the code is absent rather than pending. The
placeholder text currently reads "Not yet translated to V", which is wrong
for these four; a distinct "no V equivalent" rendering is a follow-up task
on `remark-code-tag.mjs`, not part of chapter 5.

Three of those mappings are worth naming, because they are the hybrid
earning its place. The book's one abstract `accept` and its N overrides
become the `walk_expr` signature and its N `match` arms — the same
one-to-N structure, so the line-ownership model in
[Snippets](snippets.md) splits them across the same tags Nystrom used.

`printer-main` is the one rough edge. A V program has exactly one `main`,
and `vlox/src/main.v` already has it, so Java's second entry point becomes a
plain function `ast_printer_main`. It goes uncalled, exactly as Nystrom's
does after he comments it out in chapter 6. It needs a note.

`LiteralExpr.value` is chapter 4's `?Literal` — `?(f64 | string)` — not a
new type. `nil` is the absent option, which is what Java's `null` check in
`visitLiteralExpr` tests. Chapter 7 widens it; chapter 5 does not.

One consequence surfaced during review. Java's `AstPrinter.main` builds
`Expr.Literal(123)` from an `int`, so `toString()` gives "123"; `vlox` has
only `f64`, which gives "123.0", and the chapter states its output
literally. An unmarked `literal_repr` helper in `ast_printer.v` trims the
trailing ".0" — the same thing Nystrom's `stringify` does in chapter 7,
arriving early. It stays outside the markers, exactly as chapter 4's
`Lox.error` back-reference does, so `visit_literal_expr` renders as the
two-line method Java has rather than fifteen lines of formatting the book
never shows. Chapter 7 promotes it into a marked snippet where the prose
introduces it.

## Decision 4: control flow is an error value

Chapters 6, 7, and 10 each use a Java exception as control flow: `ParseError`
to unwind to a synchronisation point, `RuntimeError` to abort evaluation,
and `Return` to leave a Lox function body. All three become V error structs
embedding `Error`, returned through `!`. Verified:

```v
struct RuntimeError {
	Error
	token Token
	m     string
}

fn (e RuntimeError) msg() string {
	return e.m
}
```

The call site recovers the payload by smart-casting inside `or {}`:

```v
value := evaluate(expr) or {
	if err is RuntimeError {
		lox.runtime_error(err)
		return
	}
	return err
}
```

`Return` is the same shape carrying a `Value` instead of a message. Using an
error to carry a normal return value reads oddly, and Nystrom says the same
thing about his `Return` exception — his note that this is an abuse of the
mechanism survives the translation intact, so it needs no note of ours.

What does need a note is the direction of the cost. Java's unchecked
exceptions cross frames invisibly; V's `!` is on every signature between the
throw and the catch. That is more typing and better documentation, and it is
why every `visit_*` method returns `!R` even when it cannot fail.

## Decision 5: `Environment` is a heap struct with an optional reference

```v
@[heap]
struct Environment {
	enclosing ?&Environment
mut:
	values map[string]Value
}
```

Verified: the chain resolves, and `if enc := e.enclosing` unwraps the parent
without a nil check. `@[heap]` is what lets chapter 10's closures keep a
captured scope alive after the call that created it returns; V's collector
handles the cycles a closure makes, so no ownership discipline is needed
beyond the attribute.

One V-specific trap found while verifying it: indexing a `map` whose value
is a sum type emits

```
warning: `or {}` block required when indexing a map with sum type value
```

so `Environment.get` must use `if v := e.values[name]` rather than a bare
index. Expect this everywhere `Value` is stored in a map — chapters 8, 11,
and 12.

## Translator's notes chapter 5 needs

One note per difference, per [Translation Rules](translation.md). Six:

1. **The generator.** Next to the `GenerateAst` section: V's sum type is the
   type description, so there is nothing to generate and no tool to write.
2. **Double dispatch.** Next to §5.3's explanation of `accept`: V's `match`
   dispatches on the variant directly, so the interface and its `visit_*`
   methods survive but the per-node `accept` collapses into one `walk_expr`.
3. **`Visitor<R>`.** V has generic interfaces, so `ExprVisitor[R]` carries
   over; but V has no method overloading, which is why `visit` is
   `visit_binary_expr` rather than an overload set.
4. **Variant naming.** `Expr.Binary` is `BinaryExpr`, because V has one flat
   namespace.
5. **The second `main`.** A V program has one entry point, so `AstPrinter`'s
   `main` is a named function.
6. **A function shown in halves.** Java declares `accept()` on the base class
   and implements it per subclass; V cannot split a function that way, so
   `base-accept-method` renders `walk_expr` with an empty `match` and
   `accept-method` fills in the arms. Neither half compiles alone. This is
   the hybrid's one visible cost and the reader is owed the warning.

Appendix II depends on notes 1 and 4 and will reuse them.

## Verification

Each decision was compiled and run under V 0.5.2 before it was written down.
The prototypes covered: a recursive sum type with a `match` printer; a
generic visitor interface with `walk_expr[R]`; the same returning `!R` with
a custom error struct; error smart-casting inside `or {}`; and an
`Environment` chain with an optional parent reference. The generic-method
rejection quoted in decision 1 is the compiler's own message.
